# Website Architecture

**Status**: LIVE (static build) + PLANNED (interactive backend layer).
**Source of truth**: `website/build.py` + `website/config/**` + the `docs/` corpus.
**Owner doc**: this file.

This document describes how the Kaiteyo website actually works today, how the
project command center fits in, and the contract the interactive backend must
obey when it ships. It follows the corpus honesty rule: **nothing on the site
may claim a status the repository does not support** (see
`docs/planning/CURRENT_STATE.md` for the status vocabulary).

---

## 1. Current architecture (LIVE)

The website is a **static site generated by a Python build** (`website/build.py`).
There is no server runtime, no database, and no authentication. Everything is
rendered at build time from files in the repository.

```
docs/  (the corpus: architecture, engineering, product, game, planning, ...)
   │
   ▼
website/build.py  ── reads ──▶  website/config/*.json   (navigation, site, themes, ...)
   │                             website/content/**     (pages, wiki, FAQ, guides, ...)
   │
   ├── renders docs/ → /docs/**            (markdown → HTML)
   ├── renders content/ → /, /features/, /wiki/, ...
   ├── renders project/ → /project/**       (command center, from config/project/* + MASTER_TODO.md)
   │
   ▼
website/dist/**   (static HTML/CSS/JS — committed per current policy; see §7)
```

### 1.1 Key inputs

| Input | Purpose | Edited by |
|---|---|---|
| `docs/**` | The documentation corpus — one truth for everything the site says | humans + AI agents |
| `website/config/site.json` | Site metadata (name, version, tagline) | humans |
| `website/config/navigation.json` | Primary navigation groups | humans |
| `website/config/themes.json` | Theme gallery definitions | humans |
| `website/config/project/*.json` | Command-center data (systems, whiteboard, roadmap, suggestions, activity) | humans/AI — with the honesty rules in §4 |
| `docs/planning/MASTER_TODO.md` | Kanban task source — **parsed, not duplicated** | humans/AI |
| `docs/architecture/decisions/*.md` | Decisions index — **parsed, not duplicated** | humans/AI |
| `website/content/**` | Page-level content (home, features, roadmap, wiki, FAQ, guides) | humans |

### 1.2 Build stages (`build.py`)

1. `copy_assets()` — static assets (styles, scripts, icons, images) to `dist/`.
2. `build_documentation()` — walks `docs/` sections, renders markdown to HTML
   under `/docs/`, builds the per-section index and the docs landing page.
3. `build_faq()`, `build_shortcuts()`, `build_changelog()`, `build_wiki()`,
   `build_guides()` — content-driven pages.
4. `build_pages()` — top-level pages (`/`, `/features/`, `/roadmap/`, …).
5. **`build_project()`** — the command center (see §2).
6. `build_trial()` — the web trial page (`/try/`, a static slice).
7. Search index assembly + global search page.

### 1.3 Templates

Jinja2, loaded from `website/templates/`. Layouts extend `base.html`; the
project pages extend `layouts/project.html` (a shell with the section rail) and
share macros in `partials/project-macros.html` (status badges, doc links).

## 2. The project command center (LIVE, read-only)

The website now includes a **public project command center** at `/project/`
with eight connected surfaces:

| Surface | Route | Renders from | Interaction |
|---|---|---|---|
| Project status | `/project/` | `systems.json` + live counters | links to docs/board |
| Kanban | `/project/kanban/` | `MASTER_TODO.md` (parsed) | client-side filter/search |
| Roadmap | `/project/roadmap/` | `roadmap.json` | links to docs + kanban package |
| Whiteboard | `/project/whiteboard/` | `whiteboard.json` | interactive pan/zoom/LOD canvas |
| Suggestions | `/project/suggestions/` | `suggestions.json` + GitHub issues link | workflow + template |
| Decisions | `/project/decisions/` | `docs/architecture/decisions/*.md` (parsed) | links to rendered ADR pages |
| Activity | `/project/activity/` | `activity.json` (real snapshot) | read-only feed |
| Contributing | `/project/contributing/` | live task lists + package knowledge | links to kanban items |

### 2.1 Single source of truth rules

1. **Tasks** come from `docs/planning/MASTER_TODO.md`. The build parses the
   table rows (ID, title, status, priority, deps, acceptance); the Kanban is a
   rendering of that file. **Never edit kanban data anywhere else.**
2. **Decisions** come from `docs/architecture/decisions/`. The build parses the
   ADR headings; the Decisions page links to the rendered pages.
3. **System statuses** come from `systems.json`, which mirrors
   `docs/planning/CURRENT_STATE.md`. When the repo status changes, update
   CURRENT_STATE.md **and** `systems.json`/`roadmap.json` together.
4. **Activity** is a dated snapshot (`activity.json`). Its `captured` field
   records when it was taken; refreshing it is a documented procedure (§6).

### 2.2 Whiteboard behavior

`whiteboard.js` renders the graph from embedded JSON. Features:

- **Pan** — pointer drag anywhere on the canvas.
- **Zoom** — scroll wheel (pointer-anchored), `+`/`−` buttons, `0` = fit,
  `+`/`−`/`0` keyboard shortcuts while the canvas is focused.
- **Semantic LOD** — three levels as you zoom out: full detail (descriptions +
  status) → node labels only → groups only. Node kinds are color-coded by
  border (system/feature/database/API/integration/game); edges are typed and
  labeled (DEPENDS_ON, USES, PRODUCES, FEEDS, CONTAINS, …).
- **Click/Enter** on a node opens its documentation in a new tab.
- **Minimap** — fixed corner overview with the current viewport rectangle.

The board is **read-only** by design. Editing it requires the backend layer
(§5, API.md).

## 3. Navigation

`navigation.json` defines four groups:

- **Learn** — Try, Download, Product, Learn, Features, Screenshots, Theme Gallery.
- **Explore** — Documentation, Wiki, Guides, Q&A, Keyboard Shortcuts, Product Roadmap, Changelog.
- **Command Center** — Project Status, Kanban, Roadmap, Whiteboard, Suggestions, Architecture Decisions, Activity, Contributing.
- **Community** — Integrations, Install, About, Community, Data & Attribution, Plugins, Credits, License, Privacy, Security.

Two roadmaps exist deliberately:

- **Product Roadmap** (`/roadmap/`) — released/historical versions timeline.
- **Project Roadmap** (`/project/roadmap/`) — forward-looking phases with status,
  linked to kanban packages and documentation. Each page links to the other.

## 4. Honesty rules (binding)

1. Every status on the command center comes from the corpus status vocabulary:
   `IMPLEMENTED`, `PARTIALLY_IMPLEMENTED`, `ARCHITECTED` (target), `PLANNED`,
   `PLACEHOLDER`, `BLOCKED`, `DONE`, `IN_PROGRESS`, `RESEARCH`.
2. `ARCHITECTED`/`TARGET` means *fully designed, not built*. The Journey nodes
   on the whiteboard are labeled Target; the roadmap page explains the label.
3. **No fabricated data**: `suggestions.json`'s item list stays empty until a
   real suggestions backend exists; `activity.json` only contains verified
   events (commits from git log, ADR dates, released versions).
4. **No fake interactivity**: the kanban is filter-only; card moves, whiteboard
   edits, and suggestion submission are documented API contracts, never
   frontend simulations with silent success.
5. Any page claiming a system is "live" must match CURRENT_STATE.md. When in
   doubt, downgrade the claim.

## 5. The interactive layer (PLANNED)

The command center surfaces were built to be upgraded in place. When the
backend ships (see API.md and DATA_MODEL.md):

- The same routes gain POST/PATCH endpoints; the static render remains the
  fallback (progressive enhancement, not replacement).
- Tasks, decisions, systems, and roadmap items keep the corpus as the
  **canonical write target** where feasible (e.g. editing a task updates
  MASTER_TODO.md, then the board re-renders). Interactive-only data (comments,
  suggestions, activity) lives in the project database.
- Realtime (WebSocket) is layered on the event bus described in API.md; the
  static pages never fake live updates.
- Permissions are enforced **server-side** (see API.md §Security). The static
  site may show/hide nothing sensitive — it contains only public data.

## 6. Maintenance procedures

### 6.1 Regenerate the site

```bash
cd website
python3 build.py
```

Requires Python 3.10+ and the packages in `website/requirements.txt`.

### 6.2 Refresh the activity feed

1. `git log --oneline -20` for recent commits.
2. Check `docs/architecture/decisions/` for new ADRs and
   `website/config/project/roadmap.json` / `docs/roadmap/ROADMAP.md` for phase
   changes.
3. Update `activity.json` (new events first, bump `captured`).
4. Rebuild the site and verify the feed.

### 6.3 Add a system / roadmap item

1. Update `docs/planning/CURRENT_STATE.md` (status) and
   `docs/planning/MASTER_TODO.md` (tasks) first.
2. Mirror into `systems.json` / `roadmap.json` (id, label, status, docs link).
3. If it belongs on the whiteboard, add the node (+ edges) to `whiteboard.json`
   and run the link check (§8).

### 6.4 Edit a kanban task status

Edit the row in `docs/planning/MASTER_TODO.md` (status/priority columns use the
documented emoji/format) and rebuild. The board is a rendering.

## 7. Known limitations / debt

- `dist/` is committed (per current repo policy) — CI regeneration is the
  paydown; see `docs/planning/TODO.md`.
- No Python in the authoring environment for some contributors; the build is
  plain stdlib + Jinja2 to keep the barrier low.
- The whiteboard data file is hand-maintained JSON; node coordinates need
  care when adding nodes (use the `fit` button to sanity-check).
- Suggestions/activity are snapshots or links until the backend ships.
- GitHub is the issue tracker; the Suggestions page links issues rather than
  duplicating them.

---

## 8. Verification checklist (run after any change)

1. `node --check website/assets/scripts/*.js` — JS syntax.
2. JSON validity: `python3 -m json.tool` on each `website/config/**/*.json`.
3. Link integrity: every `href`/docs link in the new templates resolves
   (relative links against the rendered output; run a crawl over `dist/`).
4. Status labels: grep the rendered `/project/` pages for any status word not
   in the corpus vocabulary (§4.1).
5. No orphan documents: every new file is reachable from
   `docs/README.md` or a section index.
